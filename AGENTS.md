# Правила проекта 4.0

## Проект и источники

- Отвечай по-русски, просто и кратко. Работаем только в `infecto2014-ai/msuvenirov4.0`.
- Сайт собираем заново по новой концепции. `infecto2014-ai/msuvenirov3.0` — источник проверенных данных, настоящего логотипа и фотографий, только на чтение. Не переносить его код, страницы, архитектуру и историю автоматически; старую папку neon-souvenir-studio-main не использовать.
- Постоянные правила находятся только в `AGENTS.md`, актуальные решения и состояние — в `docs/RECOVERY.md`. Более поздние явные указания владельца имеют приоритет. Полная переписка не является документацией проекта.
- Стек — Astro 5 + Preact, npm. Цены — `src/data/pricing.ts`, контакты — `src/data/site.ts`. Факты, цены, отзывы и реальные работы не выдумывать. Согласованный дизайн и бизнес-правила сохранять.
- Для новых иллюстраций использовать отдельные PNG; исходники хранить независимо. Настоящий логотип и фотографии работ не заменять генерацией. Пути и принятые решения по главной указаны в `docs/RECOVERY.md`.

## Порядок работы и контекст

1. В начале работы прочитай эти правила и краткий текущий контекст один раз; повторно читай только изменившиеся или нужные разделы. Старые планы, промпты и историю открывай по конкретной необходимости.
2. Определи границы задачи и критерии готовности. Для значимой задачи достаточно краткого плана и 3–5 проверяемых критериев; очевидная мелкая правка не требует интервью и отдельного планового документа. Уточняй только неизвестное, существенно влияющее на результат; уже согласованное повторно не спрашивай.
3. Ищи через `rg`, читай затронутые файлы и нужные диапазоны. Расширяй поиск при обнаружении зависимости. Не сканируй оба проекта целиком и не повторяй выполненный анализ без новых оснований.
4. Независимые проверки объединяй. Ограничивай вывод команд, извлекай нужные поля; не выводи целиком каталоги инструментов, большие логи, историю Git и base64 изображений. Сохраняй подробности конкретной ошибки, если они нужны для отладки.
5. Делай минимальное полное изменение: переиспользуй рабочие компоненты, избегай лишних зависимостей, абстракций, рефакторингов и переписывания исправного кода. Перед визуальной правкой измерь проблему или проверь её в браузере; не повторяй цикл догадок и пересборок.
6. В конце значимого этапа обнови текущее состояние на 5–10 строк по существу: принятые решения, важные файлы, проверенные ограничения и следующий шаг. Исправляй устаревшие сведения, не накапливай дневник и дубли между документами.
7. При переходе к крупному новому этапу предложи отдельный чат с передачей на 250–500 слов: цель, состояние, файлы, ограничения и критерии. Самостоятельно новые чаты не создавай. Для небольших связанных правок сохраняй текущий чат.

## Модели, агенты и навыки

- Выбирай минимальную суммарную стоимость завершённой задачи с учётом повторов и проверки. Для поиска и рутины подходит Luna, для обычной разработки — Sol; Astra нужна для сложной архитектуры, критической логики и трудных системных ошибок.
- Используй только реально доступные идентификаторы и настройки. Для понятных задач выбирай низкий или средний уровень рассуждений, если интерфейс позволяет; высокий повышай по сложности. Не используй `xhigh` по умолчанию. Не утверждай, что модель или настройка переключены, если этого не произошло.
- Одну-две правки делай сам. Делегируй самостоятельную подзадачу, когда выигрыш оправдывает запуск агента. Передавай цель, конкретные файлы, ограничения и проверку без всей истории (`fork_turns: "none"`, если поддерживается). Не допускай пересечения правок, сохраняй чужие изменения, проверяй результат сам. После неудачи уточняй причину, избегай бесконечных повторов.
- Применяй принципы Ponytail. Выбирай минимально достаточные навыки, обычно 1–3, для простой правки допустимо без дополнительных. Читай только выбранные `SKILL.md`; не запускай весь комплект и не создавай агента на каждый навык. Явное поручение владельца важнее стороннего workflow.
- Superpowers используй по потребности: краткое проектирование для новой функции, системную отладку для сложной ошибки, тестирование для меняющейся логики. Полный процесс, формальное ревью и отдельные планы не нужны для каждой правки текста или отступа.
- OMX и RTK применяй, если они установлены и помогают конкретной задаче. Не устанавливай инструменты ради мелкой задачи. Новые сторонние навыки, плагины и зависимости согласовывай; уже одобренные действия повторно не согласовывай. Не копируй в репозиторий весь набор навыков.

## Проверки по типу изменения

| Изменение | Обязательная проверка |
| --- | --- |
| Только документация или опечатка | Diff, смысл, актуальность упомянутых файлов, команд и ссылок. Запуск приложения и полный набор тестов не требуются. |
| Вёрстка, стили, изображения | Быстрый просмотр затронутого блока в dev-режиме; в итоге — изменённые страницы на 1440, 1024, 768 и 360 px, переполнение, консоль, клавиатура и фокус. Финальные `npm run build` и `npm run check:links`. |
| Интерактивность и анимация | Проверка сценария на компьютере и телефоне, соответствующие тесты логики; для затронутого поведения — reduced-motion и вариант без JS. Финальные сборка и проверка ссылок. |
| Расчёты, цены, смета, форма заявки, общая логика | Проверка источников данных, профильные и смежные регрессии; в конце `npm test`, `npm run build`, `npm run check:links`. Безопасность, валидацию и доступность не сокращать. |

- Не запускай полный набор после каждой промежуточной правки. Полную проверку делай на готовом логическом результате; повторяй затронутые проверки после новых изменений, ошибок или появления риска. Сначала дождись завершения текущей сборки, не запускай конкурирующие сборки одной рабочей копии.
- Для визуальных проверок используй существующий `scripts/shots.mjs` или доступный Playwright. При изменениях SEO сохраняй запрет индексации тестовой копии.
- Перед заявлением об успехе получи свежие результаты нужных проверок. Недоступную проверку и оставшееся ограничение укажи явно; не заявляй о несуществующих тестах или использованных навыках.

## Git и завершение

- Перед изменениями проверь рабочее дерево и актуальность `main`; сохрани работу с другого ПК. Перед отправкой проверь diff и секреты. Чужие изменения не удалять, force-push без явной просьбы не делать.
- По постоянному разрешению владельца после завершённой задачи и необходимых проверок выполни один итоговый commit и push готового результата в `main` 4.0. Код, изображения и документация входят в это разрешение. Промежуточные итерации отдельно не публикуй.
- Push обновляет тестовый GitHub Pages. Рабочий сервер и отправка реальных или тестовых заявок требуют отдельного явного согласия владельца.
- Итог сообщай кратко: результат, фактические проверки, существенные ограничения и статус commit/push. Модели и навыки называй только действительно использованные и существенные; код и логи целиком не повторяй.
